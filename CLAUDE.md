## Commands

Node 22, pnpm (version pinned in `package.json`, `corepack enable` picks it up). ESM throughout: relative imports use the `.js` extension even in `.ts` files.

```bash
pnpm install          # esbuild's postinstall is pre-approved in pnpm-workspace.yaml
pnpm dev                                 # no bridge: nothing goes to an LR512, the simulator at /simulator is the output
pnpm dev --bridge ws://<phone-ip>:9010   # console on http://localhost:8080, the deck and one page per fixture, reloads on change
pnpm check            # typecheck + lint + test, run before committing
pnpm typecheck        # tsc --noEmit
pnpm lint             # biome check .   (pnpm lint:fix to auto-format/fix)
pnpm test             # vitest run
pnpm test:watch
pnpm build            # tsc -> dist/, then copies src/server/public to dist/server/public
pnpm start            # node dist/index.js, with LR512_BRIDGE_URL or --bridge for an LR512
pnpm spider <phone-ip> dimmer=100 red=100   # drive the spider via the bridge; --list shows channels
pnpm laser <phone-ip> mode=manual program=pattern:12   # same for the laser; --list shows channels and range keys
pnpm laser-survey pilot --camera <camera-phone-ip> --bridge <bridge-phone-ip>   # photograph the laser at its settings, with android-camera/; --help lists the commands
pnpm rkbx-monitor   # what rkbx_link sends (OSC on UDP 4460): addresses, rate and last value, and the address to give rkbx_link; no hardware
pnpm lamp light.bar dimmer=50 red=100 fade=2   # set a Home Assistant light by entity; --list shows what Home Assistant says, --soak <minutes> is the Zigbee proof (HASS_URL and HASS_TOKEN in the environment)
pnpm perf --where receiver --effect kick --bpm 126   # how well the output keeps to the beat, against a bridge in another process, no hardware
```

Settings for `pnpm dev` and `pnpm start`, as flag or environment variable: `--bridge` / `LR512_BRIDGE_URL` (optional: without it no frame goes to an LR512, and the status bar says No bridge instead of raising an alarm; the simulator at `/simulator` works either way, and with both it gets what the bridge gets), `--universe` / `SPIDER_UNIVERSE` (0-based, default 0), `--address` / `SPIDER_ADDRESS` (default 1), `--laser-address` / `LASER_ADDRESS` (default 44, or `none` to run without the laser), `--laser-universe` / `LASER_UNIVERSE` (default: the spider's), `--show` / `SHOW_FILE` (the show file, default `show.yaml` where lightdeck is started), `--max-fps` / `MAX_FPS` (the most frames per second to send, 1 to 60, default 25), `--lead-ms` / `LEAD_MS` (how far ahead of the beat the output is made, to make up for the path to the light, default 0), `--tempo` / `TEMPO_SOURCE` (who sets the tempo at the start: `manual`, the default, or `rekordbox`), `--rkbx` / `RKBX_PORT` (the UDP port to listen on for the OSC of rkbx_link, default 4460, `off` for none; a port that is taken is said in the log and is not fatal, and in `rkbx_link`'s config `osc.source` must not be the default `127.0.0.1:4450` when it sends to another computer: `0.0.0.0:4450`), `--hass` / `HASS_URL` (`ws://<home-assistant>:8123/api/websocket`, needed when the rig file has lamps), `--hass-simulate` / `HASS_SIMULATE` (1 or true: the lamps run against a Home Assistant that lives in lightdeck, `src/outputs/hass/simulated.ts`, so no real lamp is touched and no URL or token is needed; the status bar says Home Assistant simulated in amber and the room page says so), `HASS_TOKEN` (a long-lived access token, environment only: from the shell, or from a `.env` file where lightdeck is started, which `pnpm dev`, `pnpm start` and `pnpm lamp` read with `--env-file-if-exists=.env`; `.env` is in `.gitignore`), `--rig` / `RIG_FILE` (the rig file with the lamps of the room, default `rig.yaml` where lightdeck is started; without the file there are no lamps and nothing asks Home Assistant), `--port` / `PORT` (default 8080), `--host` / `HOST` (default 0.0.0.0).

The Android bridge has its own build, see `android-bridge/README.md`:

```bash
cd android-bridge && ./build.sh             # repackages ../lightrider_classic.apk into bridge-gate.apk
```

Run a single test file or test name:

```bash
pnpm vitest run src/model/fixture.test.ts
pnpm vitest run -t "interpolates linearly"
```

Tests live next to the code as `*.test.ts`. Biome handles both lint and formatting; there is no ESLint or Prettier. The `Dockerfile` is a two-stage build producing `node dist/index.js` on `node:22-alpine`.

## Layout

- `src/model/` — the normalized fixture model (0..1 attributes, absolute Kelvin), look application and crossfade blending. Everything else builds on this.
- `src/fixtures/` — DMX fixture profiles. `profile.ts` defines controls (level, 16-bit level, strobe, function) and encodes normalized values into DMX bytes at a start address. `spider.ts` is the spider's 43-channel mode, taken from `docs/spider-dmx-channels.pdf`. Function channels (effects, reset) rest at 0 and only change through an explicit raw value. A byte range of a function channel can have a `key` to choose it by, a `name` for the page, a `scale` or `steps` when the place within the range sets something, and `when` if it only counts while another channel is in a given range; `byteInRange`, `byteForStep` and `rangeAt` turn those into bytes and back. `laser.ts` is the Alien 500 mW RGB laser, 10 channels, taken from `docs/alien-500mw-laser.html`. All its channels are function channels, and channel 1 at rest is "closed light", so the laser is dark until a mode is chosen. A control can have a `part`, which says which type of scene keeps it (`SCENE_TYPES`: `lights`, `colour`, `motion`; `controlsOf` lists a type's controls): the spider has the dimmer, the strobe and its own programs in lights and the tilts and the motor speed in motion, and the laser has mode, pattern, colour and drawing in lights and rotation, flips, positions and size in motion. The colours of the spider's lenses are in no part: its colour is a palette of the show, and a colour set by hand per lens is left out of scenes for now (the controls stay, so it can come back). The laser does not follow the palettes, so no control of it is in colour. A trigger such as the reset has none, and no scene keeps it. `SPIDER_LAYOUT` says how the spider is built, as Jeroen described it on 2026-10-14, looking at the back (the side with the LCD display and the cables): bar 1 is at the back with L1 L2 L3 L4 from left to right, bar 2 is at the front with L8 L7 L6 L5; the movement is a calibration per bar, `tiltCurve`: points of tilt and degrees from neutral (positive to the front, 90 is horizontal), straight lines between them and the bar staying put beyond the ends, so it is not linear. As Jeroen set it in the Calibrate panel of the simulator on 2026-10-14 (and as it was copied into the config from what his browser kept, because the effects run on the server and cannot read a browser): neutral is at tilt 30 for both bars, bar 1 goes from 20 degrees to the front at tilt 0 to 90 degrees to the back at 87 and 108 at 100, and bar 2 is its mirror, so the same tilt turns the two bars opposite ways (`side` says which bar is at the back); and the outer lenses of a bar face a little to the side and the inner two a little less (`aim`, degrees, 12 and 5, a guess to be tuned by eye). `bars` lists the LEDs of a bar from left to right looking at the front, which is the mirror of that, so bar 1 is `[3, 2, 1, 0]` and bar 2 is `[4, 5, 6, 7]`. The effects work on the numbers of the LEDs and do not use the order within a bar: a chase goes along bar 1 and on along bar 2 in the other direction in space, and the tilts that the motion effects send mean what the calibration says (neutral is at 0.3 and not at 0.5, and the bars turn opposite ways for the same tilt, so the tilt wave, which gives the two bars opposite tilts around 0.5, moves them the same way in space).
- `src/outputs/patch.ts` — the patch: each fixture claims its channels of a universe and gets an output of its own, so that several controllers can share one universe. Overlapping claims fail at startup.
- `src/outputs/lr512/` — WebSocket client for the Android bridge. It is push-driven: `setUniverse` is looked at at the end of the turn of the event loop, so what several fixtures made together goes out as one frame, at once. Only a frame that differs from the last one sent goes out (`skipped` counts the rest), at most `maxFps` per universe (default 25; a frame that comes sooner waits for the rest of the gap and the newest goes), with a keep-alive that starts when it connects and resends the last frame after a second without a send (or its `limits` while it has no frame: the phone closes a client that sent `limits` and is then silent for six seconds), and a held-back frame when the socket backs up. It tells the bridge its cap with a `limits` message when it connects and when it changes. A bridge that sends `alive` every second is given up on after four seconds of silence (a bridge that does not is left alone), and it polls for the bridge for as long as it is not there, also at the start, with a backoff up to 5 s, then replays the last state of every universe. `flush()` sends what is pending past the cap, for the shutdown that closes the laser. Every way an attempt or a connection can end goes through one function, and an attempt has a deadline (`connectTimeoutMs`, 4 s).
- `src/cli/` — command-line tools that use the above (`spider.ts`, `laser.ts`, and `shared.ts` for what they have in common). `rkbx-monitor.ts` is not about a fixture: it listens on the OSC port and prints what rkbx_link sends (new addresses, changes, a summary of the rate and the last value per address every two seconds, and the addresses of this computer to put in `osc.destination` of rkbx_link). Each sends its own fixture only, so the other fixture on that universe goes dark.
- `src/server/` — the backend of the console. `rig.ts` is the rig: the list of fixtures and what they share, which is the tempo (`tempo.ts`: bpm, speed of effects, where beat one lies, who sets them, `source` `manual` or `rekordbox`, and `running`, which is false while rekordbox sends no beats so that effects are idle), the blackout and the state of the link to the LR512. The rig owns the patch, so it is the one place where whole universes are put together and handed to the output. Every fixture has a controller that fits `FixtureController` in `fixture.ts`: it holds the state of one fixture, validates changes and encodes its channels. What a state or a change looks like is up to the kind of fixture. `spiderController.ts` takes `levels`, `raw`, `effect: { id, speed }` (the light effect), `motion: { id, speed }` (the motion effect, `null` is hold: the bars stay where the tilts are set) and `colour: { palette, speed }` (the id of a palette of the show, `null` for a single white, and the pace of a cycling palette, `null` for its own) and `zone` (`{ tilt: [{ min, max }, ...] }`, the window of each bar that the motion effect works inside, or `null`: then the swing limits are the window; it is the property of the scenes of type `zone`, and is applied in `renderEffects()` as `MotionModel.limits`, so a zone that lies outside the swing limits is not cut off by them: `outputValues()` cuts a tilt at the limits only when no motion effect set it). The palette is not part of the fixture: the controller looks it up by id in the `PaletteBook` that the rig owns (`rig.palettes`, kept as the show says by the playback), so an edited palette shows at once. While a light effect or a motion effect is chosen and the tempo runs it makes a frame whenever the engine asks for one (`render(at)`, see `engine.ts`): the light effect gives levels per slot and `paint` turns them into the colours of the cells, the motion effect sets the tilts (and the motor speed, for the one that says `setsMotorSpeed`), while brightness, strobe and otherwise the motor speed stay with the operator. It has an `EffectClock` for each of the three. `takesPalettes` says whether a fixture is coloured by the palettes: the spider does. `laserController.ts` takes `raw: { name: byte }`, `effect: { id, speed }` (patterns and colour chase), `motion: { id, speed }` (pulse, sweep, twist) and `colours` (its own colour setting: up to three bytes of the single colours, which the colour chase steps through, and all seven when there are none), is held closed during a blackout, and closes when lightdeck stops, because the bridge keeps holding the last frame. The laser does not follow the palettes (Jeroen, 2026-10-14). While an effect is chosen, the laser is in manual mode and the tempo runs it renders the effects when the engine asks: an effect sets the channels it drives, the others stay with the operator. An effect never opens the laser, and the controller refuses one that names the mode channel; keep that. A controller may have limits (`readLimits(value)` reads what the show file says and throws a `PatchError` for what cannot be, `setLimits(value)` puts them on what goes out, `null` is none): they belong to the show and to no scene, so they are not in `getState()` or in `snapshot`. The spider's are `{ tilt: [{ min, max }, ...] }`, a limit per bar in the order of the layout, with a bar or a key left out free and `min` below `max`; they are applied in `outputValues()` after the effects, so the state keeps what was asked and the bytes are limited, and taking them away gives back what was asked. The playback gives them to the controllers at every `follow()`, so a change of the file by hand applies too. For scenes every controller has `snapshot(type)` (what a scene of that type keeps of the fixture, without what is at rest), `check(type, part)` (refuses a part that names a property of another type) and `recall(type, part)` (sets the properties of that type; what the part does not name goes to rest, and the other types are left alone; without a part the type goes to rest, which for lights is dark and for the laser closed). The lights of the spider are the dimmer, the strobe, its programs and the light effect with its speed; its motion is the tilts, the motor speed and the motion effect with its speed; its colour is the palette with its pace, which no scene stores (the colours of the lenses by hand are in no part, left out for now but kept in the profile). The lights of the laser are the mode, the pattern, the drawing, the colour channel, the effect of the lights and the colour setting; its motion is the rotation, the flips, the positions, the size and the motion effect. `setMaster` takes the grand master, which like the blackout is kept outside the state and put into what goes out: the spider scales its control with attribute `dimmer` and nothing else, the laser is closed while the master is at 0. `darken` of the laser is final: after it nothing opens the laser again. `playback.ts` is the playback, which the rig owns: it keeps per group and per lane (lights, colour, motion, zone) what is on and whether the fixtures of the group were changed by hand since (in the properties of that lane: moving a tilt marks the motion lane and no other), and stores, renames, deletes and recalls scenes (of lights, motion or zone), sets palettes, stores and presses looks, makes, changes and deletes palettes, and makes, renames and deletes groups. A recall sets the properties of the type of its scene on the fixtures of its group only, and checks every one of them before it changes one. A palette is set on the fixtures of the group that take palettes (`setPalette`, with a pace for this use if wanted; the laser is left alone, and a group without such a fixture refuses). A look (`playLook`) sets the lanes it names as the same presses would and leaves the others; it is all or nothing; `groups[group].look = { look, changed }` says which look was set last and whether a lane it set is not what it set any more. Off is the lights: it darkens the fixtures and leaves their colours and motion, and the lanes of those stay on. After a recall, a palette or off in a group, the same lane in another group whose fixtures are all in that group is no longer on; one that shares only some of them stays on and shows as changed; other lanes are not touched. A scene that a look uses, and a palette that is on in a group or that a look uses, cannot be deleted: the operator is told what uses it. The state it tells is `groups[group][lane] = { scene, changed }` (for colour `scene` is the id of a palette) and `groups[group].look`. The rig holds the master (`getMaster`, `setMaster`), which starts at 1 every time and is not kept in the show file. `engine.ts` is the one clock that makes the frames of every fixture that animates: it ticks only while something wants frames, on a grid of a whole number of points per beat (so every beat is a point), armed for absolute moments worked out from the tempo, never faster than `maxFps` (default 25, which is what the original Light Rider app sends), rendering for the grid point and not for the moment the timer ran. A new `running` or a tap makes a frame at once. The rig owns it and the output settings (`getOutput`, `setOutput`: `maxFps` and `leadMs`, how far ahead of the beat the output is made). `Tempo` has `beatAt`, `timeOfBeat`, `epoch` (counts taps), `leadMs` and `outputBeat`; `beatAt` rounds to a billionth of a beat, because a grid point worked out as a moment came back as 12.999999999999998 and a flash on beat 13 then showed the end of beat 12. `kinds.ts` couples each kind of fixture to its profile and controller. `http.ts` serves the pages and a small API on Node's own `http` module: `GET /api/state`, `POST /api/fixtures/<id>/update`, `POST /api/fixtures/<id>/limits` (what the show limits of the fixture: for the spider `tilt`, a `{ min, max }` per bar, `{}` for none; Neither has a timer: `wantsFrames()` says whether an effect needs frames and `render(at)` makes one for the moment `at`, and they emit `wants` when the first may have changed. `getDmx()` and the `frame` events carry the frame that was sent, not a second render. An effect gets its beat from an `EffectClock` (`src/engine/effectClock.ts`) per effect of a controller (and one for the cycle of a palette), which keeps the step of an effect when its speed changes (the chase stays on its lens when ×2 or the master speed is pressed) and puts a 3% dead band on `limitSpeed`, so a track near 150 bpm with ×4 does not flap between ×4 and ×2. The sequencer (`sequencer.ts`, owned by the rig, `rig.sequencer`) runs a sequence of the show: a list of steps, each a number of bars and a look (or `off`, the lights) per group it names, set as a press on the look would set it (`Playback.playLook`, origin `sequence`), a step only setting a group whose look differs from what the sequence set last (so a press by hand stands until the next step that changes that group), starting over after the last step, one sequence at a time (starting one stops the one that runs), and stopping leaves the fixtures as they are. It counts bar lines of the tempo (four beats, beat one of the tempo starts a bar) and not time: the first step is set at once and lasts its bars from the first bar line after, a tap (`epoch`) only moves the next bar line, more than two bar lines found at once count as two, and while the tempo is not running (the music stopped) it waits. `next()` (`POST /api/sequence` with `next: true`) sets the following step at once and counts its bars from there (the moods page has a key for it). A show change that takes its sequence away stops it, one that shortens it clamps the step. Reading never writes. `file.ts` is the show file: YAML, written by the deck through the document as it was read, so comments and order of a file edited by hand stay. - `src/engine/effects.ts`, `motionEffects.ts` and `palette.ts` — what a spider shows is three things that are chosen apart and put together (Jeroen, 2026-10-14, `docs/effects-split-plan.md`). A **light effect** (twenty-two: kick, chase, bounce, bar swap, wave, sparkle, build-up, strobe burst, pump, solid, bars, alternate, spread, the five techno effects cross, tick-tock, scan, pairs and stab, and fade, strobe, seesaw and glow) is a pure function from beat to how much of each slot of the palette every cell gets, and knows no colour; slot 1 is what hits, flashes or moves, slot 2 the backdrop, slot 3 an accent. A **palette** (`palette.ts`) is a list of up to eight entries, each a colour or off, that the whole show shares; `paint` makes the colours of the cells from the levels and the palette, and a slot the palette does not have, or has as off, is dark (so with one colour a kick falls to dark, and there is no dim first colour any more). A palette is static or cycles: the list shifts by one slot per step, as a hard cut or a fade, at a pace that is one of the speeds; `colourAt` and `paint` take the step as a fraction. A **motion effect** (tilt wave, scissor, scissor with a rest, and creep, drift and slice) is a pure function from beat, tempo and, when the fixture says, how its bars turn (`motion`, the `tiltCurve` and `motorSpeedCurve` of the layout, see `curve.ts`) to a tilt per bar and a motor speed. Since 2026-10-20 (Jeroen: a tilt that is a function of the beat made the motor stutter) no motion effect sends a new tilt per frame: each sets where the bars must END UP, changing that once per leg on the beat the bar arrived at the last one, and sets the motor speed (`setsMotorSpeed`, true for all six) so that the move takes the whole leg (`pathFrame` in `motionEffects.ts` for the tilt wave, creep and drift; `scissorRender` for the scissors; slice goes at the fastest). It inverts `motorSpeedCurve` (`curveInverse`), shortens the swing around its middle when the motor is too slow for the tempo, and leaves the motor speed with the operator when the fixture gives no calibration (or the curve is the same everywhere). Keep that for any new motion effect. Two rules of 2026-10-21 (Jeroen: the effect must pop out of its background, and fades smear when fast): where a light effect has a backdrop (slot 2 under a hit, a chase, a wave; `over()` in `effects.ts`) the backdrop is only `BACKDROP` (0.1) of the colour, so a hit is ten times as bright as what it falls back to (the techno effects, `bars`, `alternate`, `fade`, `seesaw`, `glow` and `strobe` use the second colour as a colour of its own and keep it at full); and when the light effect or a cycling palette changes at 3 times per second or more (`isFast` in `palette.ts`, from the speed after `limitSpeed`: ×2 at 126 bpm is 4.2 per second) a palette that says `fade` changes hard, as a step (`renderEffects()` of the spider). The fall of a hit (`hit()`) is not touched. Any light effect goes with any motion effect and any palette. All are tested frame by frame, with no timers or state. The third slot is used by three effects, and only when the palette has one (`slots` in the context): the kick on the first beat of a bar, the tail of the chase, and now and then a spark; without a third colour they look as they do with two. The techno effects (Jeroen, 2026-10-14: the second colour as a backdrop is too light for techno) use slot 2 as a second colour that takes turns with the first, light one or two lenses at a time with a fast fall, and leave every other lens dark; without a second colour (a palette that shows one slot, like `visible: 1` of techno-pulse whose colour changes on every beat, or has an entry that is off in slot 2, like `void`) the turns of the second are the first colour again, so a scan is never silent on its way back (Jeroen, 2026-10-21; strobe too; `filled` in `EffectContext` tells which slots have a colour, the spider fills it from the palette at the step it is on). Spectrum is gone: a palette with many colours that cycles with a fade, under the spread effect, is the same picture. At speed 1 an effect changes once per beat at most (Jeroen, 2026-09-30, who found the earlier sixteenth notes much too fast): a chase takes one step per beat, a flash comes on the beat, and what moves smoothly takes a bar or more per cycle. So the build-up takes eight bars and the strobe burst four. Faster and slower is a matter of the speed, one of `SPEEDS` (÷4, ÷2, ×1, ×2, ×4), which scales the beat an effect is given. Every effect of a fixture has a speed of its own (the light effect and the motion effect each, and a palette its pace), which is part of the state and so of a scene or a look, and it multiplies with the master speed (`rate` of the tempo, the same five), which works like the grand master: set on the deck, shown in the status bar of every page, no part of a scene. Whoever renders an effect limits the product with `limitSpeed`, which halves it until a change per beat stays at or below `MAX_FLASH_HZ` (10 per second); that is what keeps the flashing within the limit. Keep both for any new effect: no more than one change per beat at speed 1, and rendered through `limitSpeed`. The two scissors work in degrees, through the `tiltCurve` of each bar: the back bar swings to the front while the front bar swings to the back so that the beams cross, and the other way to open them, as far as 60 degrees and no further than the bar that reaches the least on that side (20 degrees crossed and 60 open with the calibration of 2026-10-14, so the swing is lopsided). With that calibration it is the same tilt on both bars. The first, `scissor`, sends each bar an end point twice per cycle (one cycle in eight beats, the beams crossed on beat one and furthest apart on beat five) and sets the motor speed so that the swing takes the whole four beats: the bars never rest. The second, `scissor-motor` (called Scissor, with a rest), sends the same ends three beats before they should arrive and sets the motor speed for those three, so the bars stand still for the last beat. The tilt wave goes 0.3 of the tilt either side of the middle, high on beat 2 and low on beat 6, four beats per leg; creep sweeps over eight beats per leg; drift has legs of eight beats for the back bar and twelve for the front bar, and because there is one motor speed the back bar goes two thirds of the way the front bar goes, so both move at the same speed. Creep (both bars lean the same way and sweep slowly, one swing in four bars), drift (each bar swings on its own, in four and six bars, so the beams cross at other places every time) and slice (snaps every two beats between crossed, fanned out, both back and both forward, and sets the motor speed to the fastest) were added for the Halloween show of 2026-10-14. Neither scissor pumps the colours as the old ones did; the pump effect is the light effect to put under them. Crossfades and holds do not exist yet.

## What this is

"Lightdeck": a self-built replacement for Daslight 5 that drives two kinds of lighting from one programmable interface, for a home micro-festival (Dreamscape IV, 7 November 2026, deadline is hard):

- **DMX party fixtures** via the Nicolaudie **Light Rider LR512** interface (USB-C + wifi, ports 2430 UDP / 2431 TCP, closed protocol).
- **Zigbee lamps** via **Home Assistant (ZHA)** over the HA WebSocket API.

## Hard constraints (from Jeroen)

- Linux only. No Windows DLLs, Wine or Mac-only tools.
- TypeScript / Node.
- Runs as a container on an existing Kubernetes homelab. **Postponed (Jeroen, 2026-09-29):** for now lightdeck runs on his laptop, with the bridge on a real Android device. Do not work on the container, the manifests or the deploy until he asks.
- Operated from a web UI on a tablet.
- Reuse the LR512 if feasible, driven directly without Daslight.
- Kubernetes manifests must **not** set `metadata.namespace`; they are applied into the target namespace.
- Not in scope unless asked: MIDI controller, automatic timeline, exposing entities to Home Assistant.

## Architecture decisions already made

- **One normalized fixture model** for both worlds: attributes 0..1 (dimmer, red, green, blue, white, pan, tilt, strobe), Kelvin absolute. Each protocol gets its own **output adapter**, so the DMX backend (LR512, Art-Net, sACN) is swappable without touching the show.
- **Two speeds.** DMX runs ~40 fps (movement, chases, strobe). Zigbee is the slow ambience layer: at most ~1 command per lamp per second, always with `transition`, global budget ~10 commands/s. On a scene change send the end look once with `transition` equal to the fade time and send nothing during the fade.
- **Scenes belong to a group of fixtures, and several groups are on at once** (Jeroen, 2026-09-29): one scene per group, a scene sets the fixtures of its group only and is a complete look within it, every group has an off. This takes the place of the earlier rule that a scene is a complete look for the whole rig. A step of a sequence can name scenes of several groups and only sets what changes, so a press by hand wins until the sequence changes that group again. Groups are built, sequences are designed in `docs/show-design.md` and not built. Crossfades, with effects that keep running during them, hold buttons (flash/strobe while pressed), a master and a blackout belong to the design too.
- **Scenes have a type: lights, colour or motion** (Jeroen, 2026-10-07), for playing live: the lights say which fixtures are on and what they do, the colour says the first and the second colour, the motion says how things move. A scene stores and sets only its type, and one scene per group and type is on, so a colour scene is pressed under a chase and the chase goes on in the new colour. It needs no layers and no priorities, because every property belongs to exactly one type, so two scenes never disagree. Off is the lights. A step of a sequence, when there are sequences, names one scene per group and type. The scenes of before there were types were dropped.
- **One state per fixture** (2026-09-29). A scene sets the fixtures through their controllers, and the operator can still adjust by hand afterwards. There are no layers or priorities.
- **Scenes and sequences may open the laser**, also unattended, and there is no arm switch (Jeroen, 2026-09-29). An effect still never opens it.
- **Grand master:** it scales fixtures that have a dimmer, so what goes out is the brightness of the scene times the master. A fixture without one, such as the laser, is closed at 0 and shows what it is set to above 0. There are no faders per fixture on the deck (Jeroen, 2026-09-29). Built.
- **Tempo** is set by hand (slider, nudge, tap) or follows rekordbox through rkbx_link over OSC (Jeroen, 2026-10-21: nothing else, no complexity that is not needed). The listening to the room with a microphone was built on 2026-10-02 and taken out on 2026-10-21. Beats that stop: effects idle (not frozen, not blackout). Ableton Link was built and removed by Jeroen on 2026-10-02, because it made beat matching useless: do not suggest it again. Bars, the fraseanalyse of rekordbox (Down/Bridge as a breakdown) and the waveform were discussed on 2026-10-21 and left out on purpose: `docs/` has nothing on them, keep it simple until Jeroen asks.
- **The output path is on the beat, push-driven, and sends only frames that changed** (Jeroen, 2026-10-06; built 2026-10-07, run only against the stand-in bridge): one clock locked to the beat grid instead of a timer per controller, frames sent at once when they differ and never faster than a cap of 25 per second (what the original app does; configurable with `--max-fps` and `POST /api/output`), a heartbeat from the bridge, and the same on the phone (an APK that has not run yet). ## The LR512 protocol is the main risk

Decision (2026-09-22): reverse-engineer the LR512 protocol rather than buy an Art-Net node. The target is **full live per-channel DMX output**, the way Daslight 5 drives it. Triggering scenes stored on the device (the handoff's "plan A-min" via the STICK UDP protocol) is explicitly **not** acceptable as an end state; at most it is a diagnostic.

Jeroen drives the LR512 with **Daslight 5 on a laptop**, not the Light Rider mobile app. Transport (USB vs wifi) is still unconfirmed. Keep the Art-Net/ESP32 fallback open until the LR512 demonstrably works; only the output adapter should change.

**Resolved (2026-09-29): the LR512 is driven through an Android bridge.** The Light Rider APK was decompiled (`docs/lr512-protocol-findings.md`). The protocol lives in Nicolaudie's native library `libXHardwareLibrary.so`, and live DMX is authenticated and AES-encrypted, so it was not reimplemented. The library is Android-only, including its x86_64 build (Bionic, `libandroid`, asset manager), and no Linux build exists. So it runs where it was built to run: `android-bridge/` repackages the APK with our own classes, which open the device and serve a WebSocket on port 9010. `HANDOFF.md` §6 is superseded.

Facts that cost time to find, keep them in mind when touching the bridge:

- The LR512 identifies as **SIUDI10A** (`uid DAS:SIUDI10A:202457`), sits at 192.168.68.150 and reports **2 universes**, but only the first is usable. The vendor library gives universe `i` `min(512, licensed − i × 512)` channels (`XHL_Siudi10A::buildDongleInfo`), and an LR512 is licensed for 512. Universe index 1 therefore has 0 channels and every `sendDmx` on it returns false with `XHL_DongleLimitation`. Use index 0.
- A `sendDmx` that returns false is not a sign of a lost connection. The original app ignores the return value. The library closes the device itself when the network fails; watch the device state, not the send result.
- Scan like the original: check `enumerateAsyncIsRunning()` before `enumerateAsync()`, never scan while a device is open, open only after the scan has finished. The original sends every universe every 40 ms, changed or not.
- The vendor library must be registered with `setSoftware(XHL_SC_LightRider, "Light Rider", profile)` before `enumerateAsync()`, or discovery returns nothing.
- Discovery is UDP broadcast and the Java API has no connect-by-IP, so the Android runtime must be on the LR512's Wi-Fi. A phone works; Waydroid and emulators sit behind NAT.
- DMX ports must be set to `XHL_Output` before `sendDmx` has any effect.
- The original Light Rider app sends **every universe every 40 ms (25 per second), changed or not** (`z2/c.java`). The vendor `sendDmx` does not throttle, compare with the previous frame or wait for an answer: it makes one encrypted UDP datagram and sends it. So nothing but lightdeck and the bridge protects the LR512 from load, and 25 per second is the only rate known to be fine. Lightdeck sends up to 40.
- Node's WebSocket client sends `error` and **no `close`** when a connection attempt fails, and nothing at all when the host does not answer. A client that waited for `close` before it tried again gave up for good after the first failed try: a bridge that was not there at the start, or not back yet at the first retry 0.5 s after a drop, was never found (fixed 2026-10-06, with tests against a real WebSocket server; the fake socket of the old tests always sent `close`, which hid it). A connection that dies without a word, as when the Wi-Fi of the phone drops, is still only noticed when the operating system gives up on it: Node's client cannot ping, and the Java side answers pings but sends nothing at intervals. A heartbeat from `BridgeServer.java`, which the client would treat as dead after some seconds without, would fix that; it needs a new APK and is not built.
- Frames are whole universes: 512 bytes, up to 40 per second.

Open: since 2026-10-14 the bridge has a foreground service (`BridgeService`, notification, asks for the battery exemption) so that it can run behind other apps; it builds and has not run on the phone. One device drop (`onDeviceLeft`) was seen on 2026-09-29 with unknown cause; the reconnect loop seen later that day was our own bug, see the two points above. See "Known limits" in `android-bridge/README.md`.

`android-bridge/tools/re/` (ignored by git) holds the decompiled Java (`java-src/`, made with jadx) and `xdis.py`, an annotated arm64 disassembler for the vendor library. Use them before guessing how the library behaves.
