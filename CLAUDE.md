## Commands

Node 22, pnpm (version pinned in `package.json`, `corepack enable` picks it up). ESM throughout: relative imports use the `.js` extension even in `.ts` files.

```bash
pnpm install          # esbuild's postinstall is pre-approved in pnpm-workspace.yaml
pnpm dev                                 # no bridge: nothing goes to an LR512, the simulator at /simulator is the output
pnpm dev --bridge ws://<phone-ip>:9010   # console on http://localhost:8080, the deck and one page per fixture, reloads on change
pnpm check            # typecheck + lint + test, run before committing
pnpm typecheck        # tsc --noEmit
pnpm lint             # biome check .   (pnpm lint:fix to auto-format/fix)
pnpm test             # vitest run
pnpm test:watch
pnpm build            # tsc -> dist/, then copies src/server/public to dist/server/public
pnpm start            # node dist/index.js, with LR512_BRIDGE_URL or --bridge for an LR512
pnpm spider <phone-ip> dimmer=100 red=100   # drive the spider via the bridge; --list shows channels
pnpm laser <phone-ip> mode=manual program=pattern:12   # same for the laser; --list shows channels and range keys
pnpm beat-eval track.mp3 --tempo 126   # what the listening makes of an audio file, per second, no hardware
pnpm lamp light.bar dimmer=50 red=100 fade=2   # set a Home Assistant light by entity; --list shows what Home Assistant says, --soak <minutes> is the Zigbee proof (HASS_URL and HASS_TOKEN in the environment)
pnpm perf --where receiver --effect kick --bpm 126   # how well the output keeps to the beat, against a bridge in another process, no hardware
```

Settings for `pnpm dev` and `pnpm start`, as flag or environment variable: `--bridge` / `LR512_BRIDGE_URL` (optional: without it no frame goes to an LR512, and the status bar says No bridge instead of raising an alarm; the simulator at `/simulator` works either way, and with both it gets what the bridge gets), `--universe` / `SPIDER_UNIVERSE` (0-based, default 0), `--address` / `SPIDER_ADDRESS` (default 1), `--laser-address` / `LASER_ADDRESS` (default 44, or `none` to run without the laser), `--laser-universe` / `LASER_UNIVERSE` (default: the spider's), `--show` / `SHOW_FILE` (the show file, default `show.yaml` where lightdeck is started), `--max-fps` / `MAX_FPS` (the most frames per second to send, 1 to 60, default 25), `--lead-ms` / `LEAD_MS` (how far ahead of the beat the output is made, to make up for the path to the light, default 0), `--tempo` / `TEMPO_SOURCE` (who sets the tempo at the start: `manual`, the default, or `audio`), `--audio-record` / `AUDIO_RECORD_DIR` (write the sound that the listen page sends to WAV files there; off by default, nothing else keeps sound), `--hass` / `HASS_URL` (`ws://<home-assistant>:8123/api/websocket`, needed when the rig file has lamps), `HASS_TOKEN` (a long-lived access token, environment only: from the shell, or from a `.env` file where lightdeck is started, which `pnpm dev`, `pnpm start` and `pnpm lamp` read with `--env-file-if-exists=.env`; `.env` is in `.gitignore`), `--rig` / `RIG_FILE` (the rig file with the lamps of the room, default `rig.yaml` where lightdeck is started; without the file there are no lamps and nothing asks Home Assistant), `--port` / `PORT` (default 8080), `--host` / `HOST` (default 0.0.0.0). The settings of the listening are changed on the listen page and are not kept: they start at the defaults every time.

The Android bridge has its own build, see `android-bridge/README.md`:

```bash
cd android-bridge && ./build.sh             # repackages ../lightrider_classic.apk into bridge-gate.apk
```

Run a single test file or test name:

```bash
pnpm vitest run src/model/fixture.test.ts
pnpm vitest run -t "interpolates linearly"
```

Tests live next to the code as `*.test.ts`. Biome handles both lint and formatting; there is no ESLint or Prettier. The `Dockerfile` is a two-stage build producing `node dist/index.js` on `node:22-alpine`.

## Layout

- `src/model/` — the normalized fixture model (0..1 attributes, absolute Kelvin), look application and crossfade blending. Everything else builds on this.
- `src/fixtures/` — DMX fixture profiles. `profile.ts` defines controls (level, 16-bit level, strobe, function) and encodes normalized values into DMX bytes at a start address. `spider.ts` is the spider's 43-channel mode, taken from `docs/spider-dmx-channels.pdf`. Function channels (effects, reset) rest at 0 and only change through an explicit raw value. A byte range of a function channel can have a `key` to choose it by, a `name` for the page, a `scale` or `steps` when the place within the range sets something, and `when` if it only counts while another channel is in a given range; `byteInRange`, `byteForStep` and `rangeAt` turn those into bytes and back. `laser.ts` is the Alien 500 mW RGB laser, 10 channels, taken from `docs/alien-500mw-laser.html`. All its channels are function channels, and channel 1 at rest is "closed light", so the laser is dark until a mode is chosen. A control can have a `part`, which says which type of scene keeps it (`SCENE_TYPES`: `lights`, `colour`, `motion`; `controlsOf` lists a type's controls): the spider has the dimmer, the strobe and its own programs in lights and the tilts and the motor speed in motion, and the laser has mode, pattern, colour and drawing in lights and rotation, flips, positions and size in motion. The colours of the spider's lenses are in no part: its colour is a palette of the show, and a colour set by hand per lens is left out of scenes for now (the controls stay, so it can come back). The laser does not follow the palettes, so no control of it is in colour. A trigger such as the reset has none, and no scene keeps it. `SPIDER_LAYOUT` says how the spider is built, as Jeroen described it on 2026-10-14, looking at the back (the side with the LCD display and the cables): bar 1 is at the back with L1 L2 L3 L4 from left to right, bar 2 is at the front with L8 L7 L6 L5; the movement is a calibration per bar, `tiltCurve`: points of tilt and degrees from neutral (positive to the front, 90 is horizontal), straight lines between them and the bar staying put beyond the ends, so it is not linear. As Jeroen set it in the Calibrate panel of the simulator on 2026-10-14 (and as it was copied into the config from what his browser kept, because the effects run on the server and cannot read a browser): neutral is at tilt 30 for both bars, bar 1 goes from 20 degrees to the front at tilt 0 to 90 degrees to the back at 87 and 108 at 100, and bar 2 is its mirror, so the same tilt turns the two bars opposite ways (`side` says which bar is at the back); and the outer lenses of a bar face a little to the side and the inner two a little less (`aim`, degrees, 12 and 5, a guess to be tuned by eye). `bars` lists the LEDs of a bar from left to right looking at the front, which is the mirror of that, so bar 1 is `[3, 2, 1, 0]` and bar 2 is `[4, 5, 6, 7]`. The effects work on the numbers of the LEDs and do not use the order within a bar: a chase goes along bar 1 and on along bar 2 in the other direction in space, and the tilts that the motion effects send mean what the calibration says (neutral is at 0.3 and not at 0.5, and the bars turn opposite ways for the same tilt, so the tilt wave, which gives the two bars opposite tilts around 0.5, moves them the same way in space).
- `src/outputs/patch.ts` — the patch: each fixture claims its channels of a universe and gets an output of its own, so that several controllers can share one universe. Overlapping claims fail at startup.
- `src/outputs/lr512/` — WebSocket client for the Android bridge. It is push-driven: `setUniverse` is looked at at the end of the turn of the event loop, so what several fixtures made together goes out as one frame, at once. Only a frame that differs from the last one sent goes out (`skipped` counts the rest), at most `maxFps` per universe (default 25; a frame that comes sooner waits for the rest of the gap and the newest goes), with a keep-alive that starts when it connects and resends the last frame after a second without a send (or its `limits` while it has no frame: the phone closes a client that sent `limits` and is then silent for six seconds), and a held-back frame when the socket backs up. It tells the bridge its cap with a `limits` message when it connects and when it changes. A bridge that sends `alive` every second is given up on after four seconds of silence (a bridge that does not is left alone), and it polls for the bridge for as long as it is not there, also at the start, with a backoff up to 5 s, then replays the last state of every universe. `flush()` sends what is pending past the cap, for the shutdown that closes the laser. Every way an attempt or a connection can end goes through one function, and an attempt has a deadline (`connectTimeoutMs`, 4 s).
- `src/cli/` — command-line tools that use the above (`spider.ts`, `laser.ts`, and `shared.ts` for what they have in common). `beat-eval.ts` is not about a fixture: it listens to an audio file the way lightdeck listens to the room, through ffmpeg and the same `Hearer`, and prints what is heard per second. Each sends its own fixture only, so the other fixture on that universe goes dark.
- `src/server/` — the backend of the console. `rig.ts` is the rig: the list of fixtures and what they share, which is the tempo (`tempo.ts`: bpm, speed of effects, where beat one lies, who sets them, `source` `manual` or `audio`, and `running`, which is false while the music has stopped so that effects are idle), the blackout and the state of the link to the LR512. The rig owns the patch, so it is the one place where whole universes are put together and handed to the output. Every fixture has a controller that fits `FixtureController` in `fixture.ts`: it holds the state of one fixture, validates changes and encodes its channels. What a state or a change looks like is up to the kind of fixture. `spiderController.ts` takes `levels`, `raw`, `effect: { id, speed }` (the light effect), `motion: { id, speed }` (the motion effect, `null` is hold: the bars stay where the tilts are set) and `colour: { palette, speed }` (the id of a palette of the show, `null` for a single white, and the pace of a cycling palette, `null` for its own). The palette is not part of the fixture: the controller looks it up by id in the `PaletteBook` that the rig owns (`rig.palettes`, kept as the show says by the playback), so an edited palette shows at once. While a light effect or a motion effect is chosen and the tempo runs it makes a frame whenever the engine asks for one (`render(at)`, see `engine.ts`): the light effect gives levels per slot and `paint` turns them into the colours of the cells, the motion effect sets the tilts (and the motor speed, for the one that says `setsMotorSpeed`), while brightness, strobe and otherwise the motor speed stay with the operator. It has an `EffectClock` for each of the three. `takesPalettes` says whether a fixture is coloured by the palettes: the spider does. `laserController.ts` takes `raw: { name: byte }`, `effect: { id, speed }` (patterns and colour chase), `motion: { id, speed }` (pulse, sweep, twist) and `colours` (its own colour setting: up to three bytes of the single colours, which the colour chase steps through, and all seven when there are none), is held closed during a blackout, and closes when lightdeck stops, because the bridge keeps holding the last frame. The laser does not follow the palettes (Jeroen, 2026-10-14). While an effect is chosen, the laser is in manual mode and the tempo runs it renders the effects when the engine asks: an effect sets the channels it drives, the others stay with the operator. An effect never opens the laser, and the controller refuses one that names the mode channel; keep that. A controller may have limits (`readLimits(value)` reads what the show file says and throws a `PatchError` for what cannot be, `setLimits(value)` puts them on what goes out, `null` is none): they belong to the show and to no scene, so they are not in `getState()` or in `snapshot`. The spider's are `{ tilt: [{ min, max }, ...] }`, a limit per bar in the order of the layout, with a bar or a key left out free and `min` below `max`; they are applied in `outputValues()` after the effects, so the state keeps what was asked and the bytes are limited, and taking them away gives back what was asked. The playback gives them to the controllers at every `follow()`, so a change of the file by hand applies too. For scenes every controller has `snapshot(type)` (what a scene of that type keeps of the fixture, without what is at rest), `check(type, part)` (refuses a part that names a property of another type) and `recall(type, part)` (sets the properties of that type; what the part does not name goes to rest, and the other types are left alone; without a part the type goes to rest, which for lights is dark and for the laser closed). The lights of the spider are the dimmer, the strobe, its programs and the light effect with its speed; its motion is the tilts, the motor speed and the motion effect with its speed; its colour is the palette with its pace, which no scene stores (the colours of the lenses by hand are in no part, left out for now but kept in the profile). The lights of the laser are the mode, the pattern, the drawing, the colour channel, the effect of the lights and the colour setting; its motion is the rotation, the flips, the positions, the size and the motion effect. `setMaster` takes the grand master, which like the blackout is kept outside the state and put into what goes out: the spider scales its control with attribute `dimmer` and nothing else, the laser is closed while the master is at 0. `darken` of the laser is final: after it nothing opens the laser again. `playback.ts` is the playback, which the rig owns: it keeps per group and per lane (lights, colour, motion) what is on and whether the fixtures of the group were changed by hand since (in the properties of that lane: moving a tilt marks the motion lane and no other), and stores, renames, deletes and recalls scenes (of lights or motion), sets palettes, stores and presses looks, makes, changes and deletes palettes, and makes, renames and deletes groups. A recall sets the properties of the type of its scene on the fixtures of its group only, and checks every one of them before it changes one. A palette is set on the fixtures of the group that take palettes (`setPalette`, with a pace for this use if wanted; the laser is left alone, and a group without such a fixture refuses). A look (`playLook`) sets the lanes it names as the same presses would and leaves the others; it is all or nothing; `groups[group].look = { look, changed }` says which look was set last and whether a lane it set is not what it set any more. Off is the lights: it darkens the fixtures and leaves their colours and motion, and the lanes of those stay on. After a recall, a palette or off in a group, the same lane in another group whose fixtures are all in that group is no longer on; one that shares only some of them stays on and shows as changed; other lanes are not touched. A scene that a look uses, and a palette that is on in a group or that a look uses, cannot be deleted: the operator is told what uses it. The state it tells is `groups[group][lane] = { scene, changed }` (for colour `scene` is the id of a palette) and `groups[group].look`. The rig holds the master (`getMaster`, `setMaster`), which starts at 1 every time and is not kept in the show file. `engine.ts` is the one clock that makes the frames of every fixture that animates: it ticks only while something wants frames, on a grid of a whole number of points per beat (so every beat is a point), armed for absolute moments worked out from the tempo, never faster than `maxFps` (default 25, which is what the original Light Rider app sends), rendering for the grid point and not for the moment the timer ran. A new `running` or a tap makes a frame at once. The rig owns it and the output settings (`getOutput`, `setOutput`: `maxFps` and `leadMs`, how far ahead of the beat the output is made). `Tempo` has `beatAt`, `timeOfBeat`, `epoch` (counts taps), `leadMs` and `outputBeat`; `beatAt` rounds to a billionth of a beat, because a grid point worked out as a moment came back as 12.999999999999998 and a flash on beat 13 then showed the end of beat 12. `kinds.ts` couples each kind of fixture to its profile and controller. `http.ts` serves the pages and a small API on Node's own `http` module: `GET /api/state`, `POST /api/fixtures/<id>/update`, `POST /api/fixtures/<id>/limits` (what the show limits of the fixture: for the spider `tilt`, a `{ min, max }` per bar, `{}` for none; it goes through `playback.setLimits` into the show file, and the fixtures that cannot be limited answer 400), `POST /api/fixtures/<id>/<action>` (the spider has `reset`), `POST /api/tempo` (`bpm`, `rate`, `sync`, `source`), `POST /api/audio` (about 100 ms of raw 16-bit mono sound from the listen page, with `x-rate`, `x-index` and `x-feed` headers), `POST /api/audio/settings` (the settings of the listening), `POST /api/output` (`maxFps` and `leadMs`), `POST /api/blackout`, `POST /api/master` (`master`, 0 to 1), `POST /api/playback` (`group` with one of `scene`, whose type says what is set; `palette`, with `speed` if it should cycle at another pace than its own; `look`; or `off: true`, which is the lights), `POST /api/palettes` (`label` and any of `colours`, `mode`, `change`, `speed`), `POST /api/palettes/<id>/update` and `/delete`, `POST /api/groups` (`label`, `fixtures`), `POST /api/groups/<group>/rename` and `/delete`, `POST /api/groups/<group>/scenes` (`label` and `type`, lights or motion, stores that type of properties of the fixtures of the group as they are), `POST /api/groups/<group>/scenes/<scene>/store`, `/rename` and `/delete`, `POST /api/groups/<group>/looks` (`label`, stores what is on in the group), `POST /api/groups/<group>/looks/<look>/store`, `/rename` and `/delete`, and server-sent events on `/api/events` (`fixture`, `frame`, `tempo`, `blackout`, `master`, `status`, `show`, `playback`, `audio`, `output`). `/` goes to the deck at `/deck`, `/palettes` is the page of the palettes, `/fixtures/<id>` serves the page of that fixture's kind, `/listen` the listen page. Both controllers skip their effects while the tempo does not run, in `renderEffects()` of the spider and `outputValues()` of the laser. An idle effect neither opens nor closes the laser. Neither has a timer: `wantsFrames()` says whether an effect needs frames and `render(at)` makes one for the moment `at`, and they emit `wants` when the first may have changed. `getDmx()` and the `frame` events carry the frame that was sent, not a second render. An effect gets its beat from an `EffectClock` (`src/engine/effectClock.ts`) per effect of a controller (and one for the cycle of a palette), which keeps the step of an effect when its speed changes (the chase stays on its lens when ×2 or the master speed is pressed) and puts a 3% dead band on `limitSpeed`, so a track near 150 bpm with ×4 does not flap between ×4 and ×2. There is no WebSocket server and no login; it is meant for the home network. To add a kind of fixture: a profile in `src/fixtures/`, a controller, an entry in `kinds.ts`, and a page in `public/fixtures/`. To add a fixture of a known kind: one more definition in `src/index.ts`. Sequences do not exist yet; the playback and the tempo are where they are meant to attach.
- `src/show/` — the show. `show.ts` has what a palette, a group, a scene and a look are and reads the data of the file as a show, strictly: a key it does not know is a mistake, and `off` cannot be the id of a scene. A scene has a `type` of `lights` or `motion`: a scene without one is a mistake, and so is a scene of `colour`, because colours are palettes of the show now (Jeroen, 2026-10-14); the scenes of before there were types and the colour scenes were dropped, nothing is migrated. The palettes are the top-level `palettes:` (id, `label`, `colours` as `#rrggbb`, `#rrggbbww` or `off`, `mode` static or cycle, `change` step or fade, `speed`; up to eight colours; `engine/palette.ts` reads one). The top-level `limits:` is by fixture id and holds what the fixture's controller reads with `readLimits` (the spider: `tilt:` with a `{ min, max }` per bar); it is optional, a fixture without an entry is not limited, a fixture that cannot be limited or does not exist is a mistake, and the deck takes the key out of the file again when nothing is limited any more. `ShowSummary.limits` (the `show` event) tells the pages. A look is under its group's `looks:` and names a scene of lights, a palette (an id, or `{ palette, speed }`) and a scene of motion; it must name at least one, and what it names must be there. The ids of scenes are the group's own, whatever the type, and so are those of looks. A show without a file starts with a group per fixture and one for all of them, and with the palettes `startingPalettes` gives (a white and a rainbow); a file without `palettes:` is read the same, and the first change from the deck writes them at the top of the file. A file of step 1, with `scenes:` at the top, is read as those groups with its scenes in the group of all fixtures, and is written in the new form at the first change from the deck. Reading never writes. `file.ts` is the show file: YAML, written by the deck through the document as it was read, so comments and order of a file edited by hand stay. It is watched, and read again before every write. A file with a mistake never replaces the show that runs, and nothing is written to it until it is mended. Laser bytes are plain numbers in the file for now, not the range keys the design asks for.
- `src/server/public/` — the pages: plain HTML, CSS and browser JavaScript, no build step and no framework. There is one page per fixture, and a page holds only what belongs to that fixture: `fixtures/<kind>.html`, `.js` and `.css`. `deck.html`, `.js` and `.css` are the deck: the fader of the master, the keys of the master speed next to it, and a row per group with a row of looks and a lane per type (Lights, Colour, Motion): a key per scene in the lanes of lights and motion, a key per palette of the show in the colour lane (a group with no fixture that takes palettes, the laser alone, has one line of text there instead), and the off key at the end of the lights lane. A look key shows what it sets in a few words, and as a scene key it can be set or changed by hand. It has two modes that the URL hash selects. Show is what it opens in: a press sets the lane of its scene, palette or look on the group, and there is nothing to type and nothing that deletes. - `src/engine/effects.ts`, `motionEffects.ts` and `palette.ts` — what a spider shows is three things that are chosen apart and put together (Jeroen, 2026-10-14, `docs/effects-split-plan.md`). A **light effect** (twenty-two: kick, chase, bounce, bar swap, wave, sparkle, build-up, strobe burst, pump, solid, bars, alternate, spread, the five techno effects cross, tick-tock, scan, pairs and stab, and fade, strobe, seesaw and glow) is a pure function from beat to how much of each slot of the palette every cell gets, and knows no colour; slot 1 is what hits, flashes or moves, slot 2 the backdrop, slot 3 an accent. A **motion effect** (tilt wave, scissor, scissor by motor speed, and creep, drift and slice) is a pure function from beat, tempo and, when the fixture says, how its bars turn (`motion`, the `tiltCurve` and `motorSpeedCurve` of the layout, see `curve.ts`) to a tilt per bar and, for the one that says `setsMotorSpeed`, a motor speed. Spectrum is gone: a palette with many colours that cycles with a fade, under the spread effect, is the same picture. At speed 1 an effect changes once per beat at most (Jeroen, 2026-09-30, who found the earlier sixteenth notes much too fast): a chase takes one step per beat, a flash comes on the beat, and what moves smoothly takes a bar or more per cycle. So the build-up takes eight bars and the strobe burst four. Faster and slower is a matter of the speed, one of `SPEEDS` (÷4, ÷2, ×1, ×2, ×4), which scales the beat an effect is given. Every effect of a fixture has a speed of its own (the light effect and the motion effect each, and a palette its pace), which is part of the state and so of a scene or a look, and it multiplies with the master speed (`rate` of the tempo, the same five), which works like the grand master: set on the deck, shown in the status bar of every page, no part of a scene. Whoever renders an effect limits the product with `limitSpeed`, which halves it until a change per beat stays at or below `MAX_FLASH_HZ` (10 per second); that is what keeps the flashing within the limit. Keep both for any new effect: no more than one change per beat at speed 1, and rendered through `limitSpeed`. The two scissors work in degrees, through the `tiltCurve` of each bar: the back bar swings to the front while the front bar swings to the back so that the beams cross, and the other way to open them, as far as 60 degrees and no further than the bar that reaches the least on that side (20 degrees crossed and 60 open with the calibration of 2026-10-14, so the swing is lopsided). With that calibration it is the same tilt on both bars. The first, `scissor`, is a function of the beat (a cosine, one cycle in eight beats, the beams crossed on beat one and furthest apart on beat five), so it sends a new tilt on every frame and the motor lags behind it. The second, `scissor-motor`, sends each bar an end point twice per cycle, three beats before it should arrive, and sets the motor speed (the one effect that does, `setsMotorSpeed`; it is a property of the motion type, so no effect reaches into another type any more) so that the swing takes those three beats: it inverts `motorSpeedCurve` (`curveInverse`), shortens the swing when the motor is too slow for the tempo, and leaves the motor speed with the operator when the curve is the same everywhere. Creep (both bars lean the same way and sweep slowly, one swing in four bars), drift (each bar swings on its own, in four and six bars, so the beams cross at other places every time) and slice (snaps every two beats between crossed, fanned out, both back and both forward, and sets the motor speed to the fastest) were added for the Halloween show of 2026-10-14. ## What this is

"Lightdeck": a self-built replacement for Daslight 5 that drives two kinds of lighting from one programmable interface, for a home micro-festival (Dreamscape IV, 7 November 2026, deadline is hard):

- **DMX party fixtures** via the Nicolaudie **Light Rider LR512** interface (USB-C + wifi, ports 2430 UDP / 2431 TCP, closed protocol).
- **Zigbee lamps** via **Home Assistant (ZHA)** over the HA WebSocket API.

## Hard constraints (from Jeroen)

- Linux only. No Windows DLLs, Wine or Mac-only tools.
- TypeScript / Node.
- Runs as a container on an existing Kubernetes homelab. **Postponed (Jeroen, 2026-09-29):** for now lightdeck runs on his laptop, with the bridge on a real Android device. Do not work on the container, the manifests or the deploy until he asks.
- Operated from a web UI on a tablet.
- Reuse the LR512 if feasible, driven directly without Daslight.
- Kubernetes manifests must **not** set `metadata.namespace`; they are applied into the target namespace.
- Not in scope unless asked: MIDI controller, automatic timeline, exposing entities to Home Assistant.

## Architecture decisions already made

- **One normalized fixture model** for both worlds: attributes 0..1 (dimmer, red, green, blue, white, pan, tilt, strobe), Kelvin absolute. Each protocol gets its own **output adapter**, so the DMX backend (LR512, Art-Net, sACN) is swappable without touching the show.
- **Two speeds.** DMX runs ~40 fps (movement, chases, strobe). Zigbee is the slow ambience layer: at most ~1 command per lamp per second, always with `transition`, global budget ~10 commands/s. On a scene change send the end look once with `transition` equal to the fade time and send nothing during the fade.
- **Scenes belong to a group of fixtures, and several groups are on at once** (Jeroen, 2026-09-29): one scene per group, a scene sets the fixtures of its group only and is a complete look within it, every group has an off. This takes the place of the earlier rule that a scene is a complete look for the whole rig. A step of a sequence can name scenes of several groups and only sets what changes, so a press by hand wins until the sequence changes that group again. Groups are built, sequences are designed in `docs/show-design.md` and not built. Crossfades, with effects that keep running during them, hold buttons (flash/strobe while pressed), a master and a blackout belong to the design too.
- **Scenes have a type: lights, colour or motion** (Jeroen, 2026-10-07), for playing live: the lights say which fixtures are on and what they do, the colour says the first and the second colour, the motion says how things move. A scene stores and sets only its type, and one scene per group and type is on, so a colour scene is pressed under a chase and the chase goes on in the new colour. It needs no layers and no priorities, because every property belongs to exactly one type, so two scenes never disagree. Off is the lights. A step of a sequence, when there are sequences, names one scene per group and type. The scenes of before there were types were dropped.
- **One state per fixture** (2026-09-29). A scene sets the fixtures through their controllers, and the operator can still adjust by hand afterwards. There are no layers or priorities.
- **Scenes and sequences may open the laser**, also unattended, and there is no arm switch (Jeroen, 2026-09-29). An effect still never opens it.
- **Grand master:** it scales fixtures that have a dimmer, so what goes out is the brightness of the scene times the master. A fixture without one, such as the laser, is closed at 0 and shows what it is set to above 0. There are no faders per fixture on the deck (Jeroen, 2026-09-29). Built.
- **Tempo** is set by hand, by tapping, or by listening to the music (Jeroen, 2026-10-02): the microphone of the lightdeck laptop through the browser, as a module that can be replaced. The music stops: effects idle (not frozen, not blackout). Music without a beat: the bpm is kept. Both are settings, with those as the defaults. Ableton Link was built and removed by Jeroen on 2026-10-02, because it made beat matching useless: do not suggest it again. See `docs/auto-beat-plan.md`.
- **The output path is on the beat, push-driven, and sends only frames that changed** (Jeroen, 2026-10-06; built 2026-10-07, run only against the stand-in bridge): one clock locked to the beat grid instead of a timer per controller, frames sent at once when they differ and never faster than a cap of 25 per second (what the original app does; configurable with `--max-fps` and `POST /api/output`), a heartbeat from the bridge, and the same on the phone (an APK that has not run yet). Effects run only on the server. What is not decided and not built: what the bridge does when lightdeck goes silent (a fail-safe frame for the laser), see `docs/output-timing-plan.md`.
- **The show is one YAML file** that the deck writes and that can still be edited by hand, with hot reload (Jeroen, 2026-09-29). An invalid file must never replace or interrupt the running show. Getting it into git is a copy, not the way of working.
- **Kubernetes** (postponed, see the hard constraints)**:** `hostNetwork: true` (LAN UDP broadcast/multicast), `replicas: 1`, `strategy: Recreate` (two engines would fight over the DMX universe), pinned to a node on the same LAN.

## The LR512 protocol is the main risk

Decision (2026-09-22): reverse-engineer the LR512 protocol rather than buy an Art-Net node. The target is **full live per-channel DMX output**, the way Daslight 5 drives it. Triggering scenes stored on the device (the handoff's "plan A-min" via the STICK UDP protocol) is explicitly **not** acceptable as an end state; at most it is a diagnostic.

Jeroen drives the LR512 with **Daslight 5 on a laptop**, not the Light Rider mobile app. Transport (USB vs wifi) is still unconfirmed. Keep the Art-Net/ESP32 fallback open until the LR512 demonstrably works; only the output adapter should change.

**Resolved (2026-09-29): the LR512 is driven through an Android bridge.** The Light Rider APK was decompiled (`docs/lr512-protocol-findings.md`). The protocol lives in Nicolaudie's native library `libXHardwareLibrary.so`, and live DMX is authenticated and AES-encrypted, so it was not reimplemented. The library is Android-only, including its x86_64 build (Bionic, `libandroid`, asset manager), and no Linux build exists. So it runs where it was built to run: `android-bridge/` repackages the APK with our own classes, which open the device and serve a WebSocket on port 9010. `HANDOFF.md` §6 is superseded.

Facts that cost time to find, keep them in mind when touching the bridge:

- The LR512 identifies as **SIUDI10A** (`uid DAS:SIUDI10A:202457`), sits at 192.168.68.150 and reports **2 universes**, but only the first is usable. The vendor library gives universe `i` `min(512, licensed − i × 512)` channels (`XHL_Siudi10A::buildDongleInfo`), and an LR512 is licensed for 512. Universe index 1 therefore has 0 channels and every `sendDmx` on it returns false with `XHL_DongleLimitation`. Use index 0.
- A `sendDmx` that returns false is not a sign of a lost connection. The original app ignores the return value. The library closes the device itself when the network fails; watch the device state, not the send result.
- Scan like the original: check `enumerateAsyncIsRunning()` before `enumerateAsync()`, never scan while a device is open, open only after the scan has finished. The original sends every universe every 40 ms, changed or not.
- The vendor library must be registered with `setSoftware(XHL_SC_LightRider, "Light Rider", profile)` before `enumerateAsync()`, or discovery returns nothing.
- Discovery is UDP broadcast and the Java API has no connect-by-IP, so the Android runtime must be on the LR512's Wi-Fi. A phone works; Waydroid and emulators sit behind NAT.
- DMX ports must be set to `XHL_Output` before `sendDmx` has any effect.
- The original Light Rider app sends **every universe every 40 ms (25 per second), changed or not** (`z2/c.java`). The vendor `sendDmx` does not throttle, compare with the previous frame or wait for an answer: it makes one encrypted UDP datagram and sends it. So nothing but lightdeck and the bridge protects the LR512 from load, and 25 per second is the only rate known to be fine. Lightdeck sends up to 40.
- Node's WebSocket client sends `error` and **no `close`** when a connection attempt fails, and nothing at all when the host does not answer. A client that waited for `close` before it tried again gave up for good after the first failed try: a bridge that was not there at the start, or not back yet at the first retry 0.5 s after a drop, was never found (fixed 2026-10-06, with tests against a real WebSocket server; the fake socket of the old tests always sent `close`, which hid it). A connection that dies without a word, as when the Wi-Fi of the phone drops, is still only noticed when the operating system gives up on it: Node's client cannot ping, and the Java side answers pings but sends nothing at intervals. A heartbeat from `BridgeServer.java`, which the client would treat as dead after some seconds without, would fix that; it needs a new APK and is not built.
- Frames are whole universes: 512 bytes, up to 40 per second.

Open: since 2026-10-14 the bridge has a foreground service (`BridgeService`, notification, asks for the battery exemption) so that it can run behind other apps; it builds and has not run on the phone. One device drop (`onDeviceLeft`) was seen on 2026-09-29 with unknown cause; the reconnect loop seen later that day was our own bug, see the two points above. See "Known limits" in `android-bridge/README.md`.

`android-bridge/tools/re/` (ignored by git) holds the decompiled Java (`java-src/`, made with jadx) and `xdis.py`, an annotated arm64 disassembler for the vendor library. Use them before guessing how the library behaves.
